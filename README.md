# Visift

把图片文字整理成**整合文章、结构化笔记或字段表格**，也可按原图顺序逐字转录。默认在对话中输出，用户明确要求时导出 Markdown 文件。

> English: [README_EN.md](README_EN.md) · 同一份说明的英文版，小节逐条对应

Skill 本体只有提示词：`SKILL.md` 做入口与路由，`references/` 放四份细则，按 [Agent Skills](https://agentskills.io) 形式组织。读图与按需导出使用宿主已有能力，Skill 不附带运行脚本或依赖。仓库里的 `scripts/check-skill.mjs` 是开发用质量闸门，不参与图片整理。

## 它解决什么问题

针对默认整理任务，规则围绕以下五类问题设计：

| 通病 | 本 Skill 的做法 |
| --- | --- |
| 发多张图想整合，却得到逐图分块 | 先列内容清单，再按所选文章、笔记或表格形式整合；严格转录单独保留原序 |
| 图上有什么字就抄什么字，水印、账号名、平台 Logo 混进正文 | 先按任务保留必要文字，再用连贯性与视觉线索排除无关干扰并登记 |
| 同一个观点在图里说了三遍，就复现三遍 | 确认条件与归属兼容后，删除被完整覆盖的条目；互补、不同版本和冲突双方保留 |
| 认出字了就硬凑一篇小作文，加一堆原文没有的解释 | 每个知识点都要能在原图指到位置；指不到就删 |
| 字迹模糊时靠"常见搭配"猜通顺，还不告诉你 | 先核对同段清晰原文；仍无依据时，仅补唯一确定的 1–2 个非事实性字并标注登记 |

## 支持范围

**支持**：截图、照片、扫描件、PPT/白板拍照、UI 界面文字、文档里的表格与代码块、图表中的文字元素、滚动长图与拼接图、多张图片跨图整合成篇。

**不支持**（会明确拒绝而不是硬做）：

- 视频、动图 GIF
- 纯装饰图片、无文字插画
- 需要外部知识才能读懂的残缺内容
- 识别图中的物体、人物、场景

## 安装

把 `image-to-structured-text/` 整个目录复制到你所在 Agent 的 Skills 目录，重新加载 Skills 或重启会话即可。

| Agent | 项目级路径 |
| --- | --- |
| Codex | `.agents/skills/` |
| Qoder | `.qoder/skills/` |
| Claude Code | `.claude/skills/` |
| 通用 | 该 Agent 文档指定的 skills 目录 |

本地 Codex 会话通过 `.agents/skills/image-to-structured-text/` 发现 Skill；该副本与作为唯一源文件的 `image-to-structured-text/` 必须逐字节一致，`scripts/check-skill.mjs` 会检查。

## 使用

加载后发图 + 一句自然语言即可触发：

```
把这些截图整理成一篇内容
提取这几张图的文字，合并成文章
这 10 张课件截图帮我写成一份笔记
```

也可以指定正文形式、只要正文不要整理说明、保留逐条来源，或保存成 Markdown 文件；明确要求换语言时按翻译稿处理并声明"本文为翻译稿"。

## 输出形式

正文形式按用户请求选择，默认整合文章；详细规则见 [输出选择与交付](image-to-structured-text/references/image-types.md)。

| 形式 | 触发意图 | 处理方式 |
| --- | --- | --- |
| 整合文章（默认） | 整理成一篇、整合内容 | 按主题或流程聚合原句，保留必要列表、表格与代码 |
| 结构化笔记 | 做笔记、分点、按层级整理 | 用原文标题与原句组织要点，保留条件、示例和例外，不默认压缩摘要 |
| 字段表格 | 按名称、价格等字段列成表格 | 按指定或原文可确认的字段整理，对象、时间、版本和条件不能错配 |
| 严格转录 | 逐字转录、原样抄录、按原顺序完整提取 | 指定区域全部可见文字按原序保留；未限定区域则转录整图，不过滤、不去重、不推测补字 |

文章、笔记和表格共用同一份已核对内容；切换版式不重新概括。严格转录是独立处理模式；“提取文字”本身不自动触发它。

字段表格中，原有空单元格用 `（空）`，模糊用 `[无法辨认]`，裁切用 `[内容被截断]`；原图未提供的要求字段留空，并在「字段缺失」中登记，不算识别缺口。

统一外层为“原文标题（可省）→ 正文 → 分隔线 → 整理说明”。说明只列实际发生的处理事项；无事项且未要求来源时可省略整段。必要的缺口、核对、差异与字段缺失按位置记录。

## 交付方式

| 用户请求 | 交付方式 |
| --- | --- |
| 只说“帮我整理一下” | 直接在对话中输出 Markdown，不自动生成文件 |
| 明确要求保存、导出或 Markdown 文件 | 宿主具备文件能力时生成 UTF-8 `.md`，回读核对后返回链接和简短说明 |
| 只改变交付方式 | 复用现有正文与说明，不重新改写，也不在对话里重复文件全文 |

文件使用用户指定路径；未指定则使用当前任务的可用输出目录。除明确要求更新已有文件外，使用不冲突的新文件名保留旧版本；没有写文件能力时提供可复制的 Markdown，并说明未生成文件。

本版交付约定是对话与 Markdown 文件；HTML 和 JSON 保留为后续方向，不把“保存”理解为网站发布。

## 分批上传与后续修改

分批、追加与修正规则见 [分批上传与后续修正](image-to-structured-text/references/dedup-and-rewriting.md)。

- 用户说“还没发完 / 等发完再整理”时，只确认收到的图片范围；收到“发完了 / 开始整理”再处理。未要求等待则直接处理。
- 同一批跨消息连续编号，保存已处理、待处理和缺口的位置；追加时沿用已选正文形式和交付方式。
- 按文字密度、表格或代码复杂度、主题边界与预计长度分批；对话分批后等“继续”，文件可完整生成时直接交付完整文件。
- 追加内容先判断跨图关系，清晰补图只修复对应缺口；用户只改某处时保留其余定稿内容和顺序。
- 局部修订可在对话中只展示改动；文件仍交付完整新版，除非用户明确要求片段文件。无法读取原图或旧全文时说明缺失，不凭记忆重建。
- 已发出的批次不声称被改写；后批发现的覆盖或冲突登记为待整合修订，生成完整版本时再应用，并核对是否还有未处理图片。

## 补全规则（为什么不会变成"AI 自由发挥"）

没有可见原文可核对时，允许推测补字的前提是**四条同时成立**：只缺 1–2 个非事实性字、补的是功能成分或原文高频搭配中的缺字、不改变句意与范围、上下文唯一支持。完整实词、整句不补。

绝对不许推测补出：数字、单位、金额、时间、日期、人名、地名、机构名、产品名、版本号、专有名词、否定词、条件与程度词（如果 / 必须 / 仅 / 可能 / 不）、结论性表述、比较关系——无法核对时按原因标 `[无法辨认]` 或 `[内容被截断]`。

满足全部前提且只有唯一解才补并标注，置信度记高；有第二解就不补，不再允许“中置信度选中性词”。图片边缘截断不做推测补全。
所有补全登记位置、依据和补字；清晰原文的跨图核对单独登记，不使用 `〔〕`。详见 [补全与核对细则](image-to-structured-text/references/gap-filling.md)。

## 干扰文字怎么排除

先按任务判断保留范围：操作教程的按钮、讨论中的说话人与必要时间、用户指定提取的文案都属于内容；页码等可留作内部定位线索。再对其余文字做**连贯性测试**：它属于句子主干，还是压在上面的另一层？

看这张课件截图：

```
标题（深色块，白色粗体）：9. 获取源代码和二次开发
压在标题右侧的半透明署名：账号名 + bilibili 标识
下方气泡正文：安装所需要的依赖，以便我能运行项目！
```

内容是「9. 获取源代码和二次开发 —— 安装所需要的依赖，以便我能运行项目！」。
那串压在标题上、字号与正文不一致、带平台 Logo 的署名是**水印**，直接排除，不解释它是谁、不补充关于该账号的任何背景。

对与任务无关的文字，排除线索按以下顺序考虑，命中两条才判为干扰：

1. **跨图重复出现同一串字**（仍须区分表头、步骤和必要提示）
2. **视觉层级异常**：半透明、描边、压在主体之上、贴在边角
3. **语义与上下文不连贯**：塞进句子里读不通

常见候选干扰包括水印、平台标识、弹幕、界面元素、页眉页脚、二维码提示与推广文案；类别本身不是删除依据，用途不明就保留并注明存疑。详见 [干扰判定细则](image-to-structured-text/references/interference-text.md)。

两个细节：
- 水印看不清**不占缺口名额**（`[无法辨认]` 只留给正文内容），直接归到「未采纳」。
- 排除动作要登记在文末「未采纳」里，让过滤过程可核对，不是悄悄消失。

## 跨图整合与缺口修复

跨图比对与修复分别按 [跨图关系细则](image-to-structured-text/references/dedup-and-rewriting.md) 和 [缺口核对细则](image-to-structured-text/references/gap-filling.md) 执行。

| 情况 | 处理 |
| --- | --- |
| 重复或完整覆盖 | 对象、条件、归属兼容且信息被完整覆盖，才择一删除 |
| 同主题互补 | 按主题聚合，各自原句和独有细节保留 |
| 不同版本或说法 | 不同条件分别保留；同条件冲突或条件不明时，保留双方并在整理说明中定位差异 |
| 同段清晰度不同 | 确认同版本同片段且可见文字一致后，照抄清晰图中对应原文，记录核对来源 |

清晰图中的数字、日期等可以逐字转录；不能因为模板相似或图片后上传，就拿来补另一版本的缺口，也不能拼猜两张图都看不清的字。

每条内容在内部清单中保留图号、区域、邻近原文与去向。缺口、差异和核对记录默认提供必要定位；完整来源对照表仍只在用户要求时附上。

例如可定位为“图 3，中部第二个气泡，‘预算’之后的金额被遮挡”。宿主有局部查看能力时可针对疑点复查；仍不清楚就保留缺口，并只请求对应位置的清晰图。

补图确认对应后修复该处，更新当前缺口数和补全登记，保留核对来源。默认更新完整结果并沿用所选形式与交付方式；对话可只展示指定局部修订，文件仍交付完整新版。其他已定稿措辞保留。

## 目录结构

```
image-to-structured-text/
├── README.md                          # 本文件，给人看（中文）
├── README_EN.md                       # 同一份说明的英文版，小节结构一一对应
├── AGENTS.md                          # 给进来改这个仓库的 AI 看的规矩
├── CLAUDE.md                          # 指路牌：Claude Code 只读那个文件名
├── scripts/
│   └── check-skill.mjs                # 开发用质量闸门，不参与执行
├── evidence/
│   └── README.md                      # 运行记录的命名与格式
└── image-to-structured-text/
    ├── SKILL.md                       # 入口：模式与触发边界、8 步流程、交付路由、自检
    └── references/                    # 按需加载的细则
        ├── image-types.md             # 输出形式与模板、Markdown 交付、9 类图片细则
        ├── interference-text.md       # 干扰文字判定表 + 三种最易判错的情形
        ├── dedup-and-rewriting.md     # 跨图关系、去重边界、分批上传与后续修正
        └── gap-filling.md             # 缺口定位、清晰图核对、唯一解补字与后续修复
```

`SKILL.md` 只负责路由与硬约束，细则下沉到 `references/`，靠入口里的一句话告诉 Agent 什么时候去读哪一份——这样入口能控制在 160 行以内，长规则不会把短任务淹没。

## 质量闸门

```
node scripts/check-skill.mjs
```

零依赖，只用 Node 标准库。检查项：

- frontmatter 只有 `name` 与 `description`；`name` 与目录名一致且为 hyphen-case
- `description` 非空、单行、≤1024 字符且≤1024 字节（有些运行时按字节截断，中文一字三字节）
- `description` 保留了全部触发词（图片 / 整理 / 水印 / 干扰 / extract / transcribe / OCR / screenshot）——少一个就掉一次宿主命中，自己还看不出来
- `SKILL.md` ≤160 行；无 TODO / FIXME / 待补充 / 占位
- `SKILL.md` 里引用的 `references/…` 路径必须真实存在（防止改名留死链）
- 反向检查：`references/` 里没被入口提到的文件 = Agent 永远不会去读的死重量
- `.agents/skills/` 安装副本与源逐字节一致，且没有多余旧文件

任何一项 FAIL 退出码为 1，可以直接接进 CI。

## 测试用例

以下 9 个既有用例针对默认文章整理模式；预期行为不代表实测结果，也不作为新增输出形式或文件交付的通过记录。

| # | 用例 | 输入 | 预期行为 | 判定标准 |
| --- | --- | --- | --- | --- |
| 1 | 多张图成篇整合 | 同一主题的 5 张截图（聊天记录 + 3 条小贴士 + 1 张表格） | 输出为按主题组织的连续文章，正文中不出现「图 1」「图 2」分块 | 出现逐图分节即判失败；元信息只允许出现在分隔线之后 |
| 2 | 纯文字截图 | 一段 5 行纯文本通知，含状态栏与时间 | 5 行内容进正文，措辞不改；状态栏/时间归入「未采纳」 | 无新增句子；无改写；不虚构层级标题 |
| 3 | 带标题层级的技术文档 | 一页文档照片：1 个 H1、2 个 H2、3 行表格、1 个代码块 | 标题层级映射正确；表格行列完整；代码逐字符照抄含缩进 | 表格 3 行 0 缺漏；单位与版本号未被四舍五入；条目数与原图一致 |
| 4 | 手写笔记 + 遮挡补全 | 手写纪要照片，3 处字迹模糊，其中 1 处缺一个连接词 | 缺字满足全部前提且唯一确定才补并加 `〔〕`；其余 `[无法辨认]`；文末逐条登记依据 | 补全未登记 = 失败；补出事实性内容（数字/结论）= 失败 |
| 5 | 水印与干扰文字 | 课件截图：标题「9. 获取源代码和二次开发」+ 压在标题上的半透明署名与平台 Logo + 气泡正文 | 正文只写标题与气泡内容；署名与 Logo 归入「未采纳」并计数 | 正文出现水印字样 = 失败；为水印补充账号背景 = 失败；把看不清的水印标成 `[无法辨认]` = 失败 |
| 6 | 事实性缺字不许补 | 截图里金额被光标挡住：「预算 12＿ 元」 | 输出「预算 12`[无法辨认]` 元」，不猜"0/00/5" | 补出任何数字即判失败 |
| 7 | 图表中的文字 | 柱状图截图：标题、双轴标签、图例、4 个数据标签 | 文字照抄进文章；不描述柱形高低、不推断趋势 | 出现"上升/下降/说明/表明"等推断词即判失败 |
| 8 | 无文字图片 | 一张风景照或纯图标插画 | 回复「图中没有可提取的文字」，可提示支持范围 | 出现任何画面描述即判失败 |
| 9 | 含重复内容的长文 | 公众号长文：同一观点在开头、中段、结尾各表述一次，措辞递进详细 | 保留信息最全的一条写入唯一位置，删除另 2 条并计数 | 未把两条片段拼成新句；未丢失独有细节；正文中该观点只出现 1 次 |

补充回归用例（可选）：竖排/分栏排版、原图错别字保留 `[原文如此]`、内容在图片边缘被截断、用户要求可追溯时才附来源对照表。

### 测试结果

**尚未按用例留档。** 上表是设计好的用例与预期行为。示例那几组确实用真实截图跑过，但没有按这 9 条判定标准逐项打分，所以不构成通过记录——不要把任何一行当成已通过。

### 运行规程

一次运行要满足下面全部条件，才算一条能核对的记录：

1. 一组图配同一句请求语：「把这些图整理成一篇内容，重复的合并，看不清的标出来」。
2. 记下当时的 Agent 名、模型名、日期和 `SKILL.md` 行数——版本变了就是另一次实验，不能混着统计。
3. **第一次输出原样冻结**，事后一个字都不许改，人工修正也不行；要修就另起一条记录，写明是第几次。
4. 按「判定标准」逐项写"过 / 不过 + 看到了什么"，重点核对 4、5、6、8 号的判失败条件——这几条守的是防编造与过滤干净的底线。
5. 通读输出判成文质量：像文章还是像逐图清单，后者说明第 7 步「按所选形式组织正文」需要加强。
6. 9 组没跑完就不写"整体通过"，跑完几组写几组。
7. 为了验证判定标准而手工造的坏样本，只证明标准本身有效，不算 Skill 的成绩。

补进表格时"预期"与"实测"分列，实测不许覆盖预期。

### evidence/

每次运行落一个文件：`evidence/tc<编号>-<日期>-<agent>-<模型>.md`，里面依次是输入图片清单、原样输出、逐项判定、结论。README 只写结论并指过去，不写没有出处的"效果很好"。

## 设计取舍

- **组织但不创作**：文章、笔记、表格只调整结构，禁止新增概念、拔高结论、补写总结段；严格转录保留原序。
- **只删不改**：去重靠删除整条冗余表述，绝不把两句合成一句"更好的话"——合并就是一种编造。
- **补全必须留痕**：补的字写进 `〔〕` 并登记依据，让"整理"和"改写"的边界对读者可见。
- **过滤也要留痕**：先保留任务所需文字；被排除的无关水印、装饰、推广文案在「未采纳」里按类别计数，不做无声删除。
- **短输出是正确答案**：图片信息少时文章就是短的，Skill 里明确禁止为凑篇幅扩写。
- **不做画面描述**：这是文字整理工具，不是图像理解工具，边界写死在执行流程最前面。
- **正文不翻译**：文章语言跟随图片原文语言，中文图出中文文章，英文图出英文文章；元信息与拒绝理由用用户对话的语言，两者可以不同。要换语言成文就是翻译请求，整篇声明为翻译稿。
- **冲突时的裁决顺序**：忠实 > 可读 > 简洁。读不顺时不牺牲忠实，简洁排在最后。

## 约定

- YAML frontmatter 只用开放规范字段 `name` 与 `description`，不依赖特定 Agent 的专有字段。
- `description` 用「当……时使用」的触发条件写法，单行。
- 标注符号固定五个：`[无法辨认]`、`[内容被截断]`、`[原文如此]`、`〔〕`、`（空）`，不自造新标记。
